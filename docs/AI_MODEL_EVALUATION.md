# FoodBridge AI: Surplus Forecaster Evaluation

> **Read this first.** The shipped model (`sf-20261103-c261c11a`) was trained and
> evaluated **only on SYNTHETIC data**. Every number below describes how well it
> forecasts a simulation that we wrote ourselves. It says **nothing** about
> accuracy on real restaurants. The model, its metadata and every API response
> carry `training_data_label = "SYNTHETIC"`.

## 1. Task

Forecast `surplus_qty` (prepared − sold) for one restaurant, one meal period
(`BREAKFAST | LUNCH | DINNER | ALL_DAY`) and one future date, 1–31 days after
the last history row. Output: an integer point forecast and an approximate
80% range. A forecast is **never** a donation.

## 5. Features

All features come from one shared module, `app/services/features.py`, used by
both `training/train.py` and the API, so serving features are identical to
training features (a test checks the API forecast equals the model applied to
training-path features for the same history).

For a target date, only history rows of the same restaurant and meal period
**before the cutoff** are used. In training the cutoff is `target − h` with a
horizon `h` drawn uniformly from 1–31 days per row (seeded), which mirrors how
the backend forecasts up to 31 days past the last history it sends. A target
needs at least **14** history rows, otherwise the API returns
`insufficient_history` and no number.

Quantities are divided by a per-restaurant **scale** = mean `prepared_qty` of
the last 28 rows (≥ 1). The model predicts surplus in units of scale, which
makes it independent of restaurant size and unit; predictions are multiplied
back, clipped at 0, and capped at `planned_prepared_qty` when given.

| Feature | Definition |
|---|---|
| `last_surplus_norm` | last observed surplus / scale |
| `roll7_mean_surplus_norm`, `roll28_mean_surplus_norm` | mean surplus of the last 7 / 28 rows / scale |
| `roll7_std_surplus_norm` | standard deviation of the last 7 rows / scale |
| `same_weekday_mean4_norm` | mean surplus of the last 4 rows on the target's weekday / scale (falls back to the 28-row mean) |
| `surplus_ratio_28` | Σ surplus / Σ prepared over the last 28 rows |
| `prepared_ref_norm` | `planned_prepared_qty` if given, else mean prepared of the last 7 rows, / scale |
| `planned_prepared_provided` | 1 if `planned_prepared_qty` was given (30% of training rows simulate this with the actual prepared quantity) |
| `expected_surplus_norm` | `prepared_ref_norm × surplus_ratio_28` |
| `horizon_days` | days between the last history row and the target (clipped to 31) |
| `dow_0` … `dow_6`, `is_weekend` | day of week (one-hot) |
| `month_sin`, `month_cos` | month, cyclic encoding |
| `is_holiday`, `has_special_event` | flags supplied with the target |
| `meal_breakfast`, `meal_lunch`, `meal_dinner`, `meal_all_day` | meal period (one-hot) |

`restaurant_type` and `restaurant_size` are **not** features (the backend does
not send them); they are used only to break down residuals.

## 6. Chronological split (by target date, no shuffling)

## 7. Results

MAE and RMSE in meals per service period.

| Model | Validation MAE | Validation RMSE | **Test MAE** | **Test RMSE** | Serialized size |
|---|---|---|---|---|---|
| Baseline: same-weekday trailing mean (last 4 same-weekday rows) | 19.935 | 31.615 | 20.875 | 33.240 | (no model) |
| **LinearRegression (selected)** | **18.090** | **28.433** | **19.406** | **30.109** | 0.9 KiB |
| RandomForestRegressor (120 trees, depth 12, leaf 20) | 18.099 | 28.549 | 19.358 | 30.110 | 2,022 KiB |
| HistGradientBoostingRegressor (400 iters, lr 0.05) | 18.758 | 29.224 | 19.419 | 30.085 | 570 KiB |

**Selected model: LinearRegression**, by the pre-declared rule "lowest
validation MAE; must beat the baseline, otherwise ship the baseline".

- Against the baseline it reduces test MAE by **7.0%** (20.875 → 19.406) and
  test RMSE by **9.4%** (33.240 → 30.109). On validation: −9.3% MAE.
- The three learned models are within 0.05 MAE of each other on test (Random
  Forest is 0.05 lower there). That difference is noise-sized and was not used
  for selection, since choosing on the test set would leak it. Linear
  regression is also the smallest and most transparent artifact.
- The modest gain is expected for this simulation: most of the remaining error
  is irreducible demand noise and unflagged rain shocks that no feature can see.

Shipped artifact: `app/models/artifacts/surplus_forecaster.joblib`, 1,134 bytes,
sha256 prefix `c261c11a`, plus `surplus_forecaster.meta.json`. Retraining
reproduces the same artifact bytes.

### 7.1 Prediction interval

`lower_qty`/`upper_qty` = point forecast + the 10th/90th percentiles of
validation residuals (normalised by scale): **−0.141 × scale** and
**+0.178 × scale**. On the test split the empirical coverage is **74.5%**,
below the nominal 80%: the test period (August–October, monsoon and festival
season) is noisier than validation. Treat the range as approximate.

Observations:

- Error grows with restaurant size in absolute terms, but relative to the
  mean actual surplus it is flat: MAE / mean surplus = 0.64 (small), 0.62
  (medium), 0.62 (large). Single-period surplus is inherently noisy.
- Weekends, holidays and special events are the hardest cases. Holiday
  effects differ by restaurant type (office canteens over-prepare, family
  restaurants sell out) and a single `is_holiday` flag cannot tell them apart.
  Events are only a yes/no flag; their size is not modelled.
- Accuracy barely degrades with horizon because the simulated demand level
  drifts slowly; real data may degrade more.
- ALL_DAY (bakery-cafés, only 4 restaurants) has the largest bias (+3.7):
  little training data.

## 10. Limitations

1. **Synthetic ≠ real.** The simulation encodes our own assumptions about
   weekly patterns, holidays and noise. A model that does well here can do
   badly on real restaurants. Real performance is unknown until the model is
   retrained and re-evaluated on real donor history.
2. Holiday dates are approximate and the holiday effect is a single flag.
3. Special events are a yes/no flag. Size and type are ignored.
4. The interval under-covers on the test period (74.5% vs 80%).
5. With fewer than 14 history rows for a meal period, no forecast is made.
6. The model never sees restaurant type, location, weather, menu or price.
7. A forecast is not a donation and never reserves or promises food.

## 11. Retraining with real data

1. Export `restaurant_daily_metrics` to CSV with at least these columns:
   `restaurant_id` (the donor id), `date` (YYYY-MM-DD), `meal_period`,
   `prepared_qty`, `sold_qty`, `surplus_qty`, `is_holiday`, `data_source`
   (`DONOR_ENTERED`, `IMPORTED` or `SYNTHETIC`). `special_event`, `unit`,
   `restaurant_type`, `restaurant_size` and `holiday_name` are optional.
2. Run, from `ai-service/`:
   ```bash
   .venv/bin/python -m training.train --dataset /path/to/export.csv
   ```
   The training data label is derived from `data_source`: only
   `DONOR_ENTERED`/`IMPORTED` rows → `REAL`; any mix with synthetic rows →
   `MIXED`; otherwise `SYNTHETIC`. It cannot be overridden by hand.
3. Review the printed metrics and `training/reports/training_report.json`.
   The pipeline ships the baseline automatically if no model beats it on
   validation. Check interval coverage and per-group residuals.
4. Run the tests (`.venv/bin/python -m pytest -q`). `test_model_artifact.py`
   checks that the recorded test MAE is not worse than the baseline's, that
   the feature list matches, and that the artifact hash matches its metadata.
   `test_metadata_is_labelled_synthetic_and_complete` and
   `test_generator_reproduces_shipped_dataset` assume the bundled synthetic
   dataset and must be updated when the shipped model changes to real data.
5. Commit `app/models/artifacts/*` and register the new version in
   `model_versions` (version, algorithm, metrics, `training_data_label`,
   `artifact_sha256` from the meta file).
